# 如何构建智能体记忆：知识住在哪里？

原文链接：<https://x.com/devstein64/status/2094440843595706863>

原文作者：Devin Stein

![文章头图](https://pbs.twimg.com/media/HRDyjcRa4AACG58.jpg:large)

作者：[Devin Stein](https://x.com/devstein64)（[@devstein64](https://x.com/devstein64)）

发布于 2026 年 8 月 31 日。

**在谈「存哪儿」之前，得先想清楚智能体的知识长什么样——文件、数据库、向量库都只是后面的选项。**

本系列第一篇把智能体记忆拆成四块：表示与存储、提取、检索、维护。熟悉数据库的话，可以粗略对应 CRUD：知识怎么存？怎么写进去？怎么再找回来？怎么保持更新？

这篇只谈第一个大问题：智能体的知识**到底住在哪**？

直觉答案是「数据库里」——但步子迈太大了。在决定放哪儿之前，得先决定知识**是什么形态**。

## [记忆长什么样？](#what-does-a-memory-look-like)

「存储」里其实藏着两个决策。**表示（representation）**是知识本身的形状；**物理存储**是托住它的系统。

一段记忆可以是一段 Markdown、一组事实、主题层级，或一张连起实体与关系的图。这些都可以放在文件、Postgres、向量库或更专门的系统里。差别在于：物理存储相对好换，**表示**却决定了智能体怎么理解、怎么操作这些知识。

最简单的一端，记忆就是文本：`AGENTS.md`、`CLAUDE.md`、历史会话转录、或抽出来的事实列表。再往上可以加关系：产品有功能、GitHub issue 被 PR 关闭、事实归属某个主题——关系可以长成树，也可以长成更丰富的图。

实践中，多数记忆系统最终会混用几种形态，没有一种表示能通吃所有场景。

## [用文件就能走很远](#you-can-get-surprisingly-far-with-files)

智能体记忆能放很多地方：少量信息直接塞进上下文窗口；语义检索走向量库；关系放图数据库；给智能体 SQLite 或 Postgres，用 SQL 查记忆。

也可以放在一个目录里。

听起来过于朴素，却成了智能体系统里相当好用的一类模式。第一代 LLM 应用几乎把检索等同于 RAG：全量嵌入、扔进向量库、按语义相似度搜。

后来编程智能体把 bash 用得炉火纯青。

它们会逛目录、跑 `grep` 和 `rg`、跟链接、看文件名、并行读很多文件。文件系统不只是存东西的方便场所，也是**当今编程智能体已经极其熟练的接口**。

所以如果从零搭记忆，文件往往是很好的起点。更难的问题不是文件放哪，而是**里面写什么**。

## [把「发生了什么」和「什么是真的」分开](#separate-what-happened-from-what-is-true)

在 Dosu，我们把记忆粗分成两类：**制品（artifacts）**和**知识（knowledge）**。

制品是「发生了什么」的记录。Slack 线程是制品，PR、Linear 工单、会议转录、设计文档、智能体会话 trace 也是。它们保真、保留原始上下文，但**不一定是真的**。

设计文档可能描述从未落地的架构；Slack 对话可能解释的是一年前的行为；工单告诉你功能为何创建，却不告诉你功能今天怎么工作。

制品是**证据**。**知识是智能体当前应当相信为真**的东西。

这个区分重要，因为有用的记忆几乎总要抽象。我们不想让智能体每次理解系统原理都重读六个月 Slack；要把历史收成简洁、可用的东西。

借用数据库类比，知识可以看成**制品上的物化视图（materialized view）**：制品保留发生了什么，知识抓住**现在**什么重要。

关键是保持两者之间的连接。每次让 LLM 总结对话、抽事实、合并多源，都是在做**有损变换**，信息会丢——这往往正是抽象的价值。

麻烦出在把来源扔掉。知识应指回生成它的制品。多数时候智能体走快车道：这是我们目前的信念；细节要紧时，再往下挖：我们为什么相信这个？何时变的？原始讨论是什么？

这样既有抽象的效率，又不牺牲底层历史的保真度。

一旦知识成为「canonical」，另一个问题立刻出现：它会**过时**。

## [知识需要版本控制](#knowledge-needs-version-control)

制品是历史的。发生了就是发生了。知识不同——它代表世界的**当前状态**，而世界一直在变。

记忆写「认证用 API key」，团队明天迁到 OAuth，旧记忆不只是没那么有用，而是**错了**。

这也是 Git 对知识特别有吸引力的原因之一。Git 不只告诉你文件**现在**长什么样，还告诉你**怎么变的**：看历史、看 diff、重建某个时间点上的真相。

但对智能体记忆来说，Git 里还有一个可能更重要的概念：**分支（branching）**。

想象智能体在 feature 分支上实现 OAuth。组织当前知识说认证用 API key；任务做到一半，系统已改，在**工作分支**里 OAuth 已可用。两句话都对，取决于你看的是哪个「世界版本」。

第二条事实不该在功能真正合并前变成组织知识。智能体真正需要的是：共享的组织知识，加上一层临时的、任务特定的**叠加层**，表示它当前操作的世界。

代码合并时，知识也可以一起合并。

智能体承担更长、更自主的工作时，我认为这会越来越重要。我们不仅要更新记忆，还要能**分支、合并、调和知识**。

当然，这又像是更多要维护的知识——于是下一个问题：到底该存多少？

## [知识是一种缓存](#knowledge-is-a-cache)

很容易把理想的智能体记忆想象成「记住一切」。我觉得那是错误目标。

制品相对便宜：Slack 消息发生了就存，会话发生了就存，历史记录不必反复改。

知识有**持有成本**。你写了一份关于认证系统如何工作的 canonical 说明，就造出了一个必须跟认证系统**保持同步**的东西。功能、服务、客户流程、决策、惯例、内部流程——在大组织里乘起来，就是极贵的维护问题。

更好的视角是把大量智能体知识当成**缓存**。缓存存在，是因为有些信息重算很贵；智能体知识同理。

智能体花二十分钟追十二个服务的调用链，搞懂计费架构——这是昂贵的上下文。若接下来二十个智能体都要重复同一趟调查，就把结果存下来。

若它只需知道某服务跑在哪个端口，答案就在明显的配置文件里——直接读文件。为这个事实再维护第二份表示，可能比现场重算还贵。

这就给「什么该进记忆」提供了一个框架。有些知识**不可替代**：人说「不能删这行为，最大客户依赖它」——这事实别处可能没有，不记下来就没了。

有些**重算很贵**：要搜二十个文件、三个服务、六段历史讨论才懂——适合物化。有些**天天用**：单次发现不贵，但反复发现浪费。

其余都可以当作 cache miss。

目标不是让智能体记住一切，而是记住那些**记住比重新发现更便宜**的东西。

## [从简单开始](#start-simple)

看今天的智能体记忆赛道，很容易得出结论：得先上图数据库、向量检索、时序关系、本体论和一套新基建才能开工。

多半不用。

若我今天从零搭内部记忆系统，会从 **Git 里的文件**开始。智能体会用，人会审，历史和 diff 白送，也不必在还没摸清什么重要之前就预测所有未来需求。

然后看哪里会崩。找不到信息就改进检索；关系重要了再加结构；智能体反复做同一趟昂贵调研就把结果物化；canonical 知识变太快、人工维护不过来，就建更好的维护系统。

若不想自己琢磨这些，用 [Dosu](https://dosu.dev) 也行——这正是我们天天在解决的问题。

智能体记忆行业也走过有趣一圈：从越来越复杂的检索与图架构，到重新发现「仓库里一堆组织良好的 Markdown」往往出奇地好用。

这不代表 Markdown 是最终形态，而是说**复杂度要挣来**。

从能工作的最简单表示起步；保留底层制品；物化值得维护的知识；让系统里的失败告诉你下一步该加什么复杂度。

当然，知识长什么样、住哪里，只是问题的一半。知识总得**先写进去**。
