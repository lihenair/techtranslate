# 你需要软件工厂吗？

原文链接：<https://x.com/addyosmani/status/2092865809299476767>

原文作者：Addy Osmani

![文章头图](https://pbs.twimg.com/media/HQrfzg8bQAAG7fK.jpg:large)

作者：[Addy Osmani](https://x.com/addyosmani)

发布于 2026 年 8 月 27 日。

**软件工厂是围着软件工作转的可重复环。能上线的代码，仍需要人的品味与所有权——以及你到底要不要工厂。**

软件工厂是围着软件工作转的可重复环。若你在建软件工厂，能上线的代码仍需要人的品味与所有权。下文会聊这个，也包括你是否*已经*需要工厂。

若你要建：

- 前期多半要人在环里：定产品意图、系统设计（如果你在乎）、以及质量门槛。

- 要审代码（「开着灯」的工厂），但故意把审力用在最需要的地方。我发现要盯紧自动化背压（back-pressure）在哪儿断掉，或可维护性取舍该落在哪儿。

- 尽量让质量检查尽早、持续发生。不必全上，但可包括类型系统、自动化测试、变异测试（mutation testing）、安全扫描，以及架构规则的 lint。

- 检查条数 ≠ 质量。你得多试，找出信噪比最好的那套检查；准备好有意收紧或放松约束。

工厂要建成：人的部分品味写进环境，Agent 拿出「活干对了」的证据，而人仍然「拥有」什么进生产。

## [你真的需要软件工厂吗？](#do-you-really-need-a-software-factory)

**按我的经验，用现成的编码 harness 就能走得很远！** 比如 Claude Code 或 Codex、多会话、把验证与约束写进规格。你甚至可以把一批 GitHub issue 扔给它们，附上实现标准与人参与标准。Claude Code routines，以及 Copilot / Codex 云端 Agent，已经能给你定时或事件驱动的环，不必自建基础设施。

工厂值得上，是在你需要**可重复、一致的跑法**，在 Agent 之间交接活，防止两个会话抢同一条 issue，留住证据，并在评审落后时暂停生产。

![](https://pbs.twimg.com/media/HQrM7D8aAAAtxmj.jpg)

开头我说：**软件工厂是围着软件工作转的可重复环**。其实可以用一条提示词演示一个很小的工厂环：

> 改代码前先读 GitHub issue #123 与仓库说明。
>
> 只实现写明的验收标准。不要改鉴权、计费、迁移，也不要改既有测试断言。在分支上干活，保持 diff 可审。
>
> 跑 npm run lint、npm test 和 npm run build。若必跑检查跑不了，停下来说明原因。开一份 draft pull request，写明跑过的检查、剩余风险，以及仍需人拍板的决定。不要合并。

可以用 goal 一直推到检查通过；也可以轮询带特定标签的 GitHub issue，或每天早上审开放的 PR。分支保护可强制合并边界；人留在环里：挑什么算 ready、做评审、做最终合并等。

**当你需要事件驱动的工作队列（例如 Slack 触发、GitHub issue、Linear、待办积压）在隔离云环境里跑分诊、实现与测试，并带明确的人盯梢时，再加软件工厂。有些人把环的末端接到监控 Agent：盯生产、开 issue，再回到分诊。**

按我的经验，工厂真正有用，是在难点变成：让不同次跑法行为一致、在 Agent 之间交接、避免不同会话认领同一 issue、保全证据，以及人审跟不上时停住生产。

解法听起来可能有点无聊。比如 Warp 提到把[每条进来的 issue 分诊](https://www.warp.dev/blog/how-to-build-a-cloud-software-factory-the-automatic-triage-skill)成四种状态之一——ready-to-implement、ready-to-spec、needs-info、wait-to-implement——标签本身会触发下一个 Agent。

![](https://pbs.twimg.com/media/HQrM9RabcAADTDo.jpg)

这枚标签一次干好几件事：它是队列，是锁；会话只捡标成 ready 的，人也得以把东西先停着，而不必永久说不。

工作流上，和只用 Claude / Codex 既有相似也有差别：

- **转向（Steering）**：Agent 需要纠偏时，你可以给输入、改方向

- **通知（Notifications）**：工厂说自己被卡住了——需求含糊、开始碰风险，或需要人输入（转向）

- **交接（Handoff）**：把任务、状态与上下文在云工厂 / 另一 Agent / 人审之间挪动。好的交接会记下发生了什么、还剩什么、为什么要交接。

**好的工厂里，人不只限于最后审一份 diff、点批准。他们可以早期定型、实现中转向、扛过交接，或拦住上线。**

验证是负责任的工厂花很多时间的地方。后面还会再写。

![](https://pbs.twimg.com/media/HQrM_YNaAAAgCPX.jpg)

若你认定需要软件工厂，自建不是唯一选项。把基础设施撑到能扩工厂很费事，你或许该想买还是建。[Factory.ai](https://factory.com/product/software-factory)、[Devin](https://devin.ai)、[Warp](https://www.warp.dev/blog/how-to-build-a-cloud-software-factory-the-automatic-triage-skill) 和 [HumanLayer](https://www.humanlayer.dev/) 都在卖这类环的一部分。

## [我实际把注意力花在哪儿](#where-i-actually-spend-my-attention)

过去一年我日常做软件的体验变了很多。我越来越多讲：用 Agent 并行干活，往「开着灯」的软件工厂挪。很多人问：这些词到底什么意思？你在建什么？用在哪类项目上？大致是这些：

![](https://pbs.twimg.com/media/HQrNBRYaEAAnJn3.jpg)

很普通的一天，我有一个更简单的开灯工厂。可以有任务在云上跑。一半可能是跟我合作的小公司的生产客户应用——有真用户、真鉴权、支付、订阅，风险很实在，必须小心。你不能只说「Agent，去干」，却没有测试、约束和质量检查。

我也可能做开源、给书写配套站、做工具、做自己的应用。这些应用种类差很多；有时共同点只是用来干活的工具。可能在做迁移；另一些是扎实的功能开发。爆炸半径也可能差很多。

所以当你开始想：我们越来越多并行、想提速、提生产力、提自主性——也就是更信任系统——你必须想清楚：哪些地方绝对要人审代码、要人输入。

很多要放在前期：规格、需求、产品长什么样、产品意图是什么；然后怎么验证 Agent 真干对了、没弄坏既有系统、达到你的质量门槛。

因此生成代码未必是最该担心的部分。上下文够时，Agent 能写实现、跑测试、看失败、改代码。**我们要到达的是：环境里已经写进足够的人味，我们信得过正在造的东西，好把人的注意力用在最需要的地方。**

也有人反驳：我不信你能把这些大量自动化掉。并不是说我们要全自动化。但以现在生成的代码量，人不现实去读完每一行——尤其我们多数时候不是在造火箭，而是在造 UI、全栈应用。

判断与品味最好用在最需要的地方：系统里风险最高的部分？人味该落在哪？可以是前端，可以是系统怎么运作。不必 100% 都要人盯。

## [我的认知带宽跟不上 Agent](#my-cognitive-bandwidth-does-not-scale-with-the-agents)

现实是：我们现在可以并行拉起几十、几百、几千个 Agent，但你自己的认知带宽不会同样扩展。这会喂养认知债或理解债——我以前写过。

![](https://pbs.twimg.com/media/HQrND4YbAAA0nmH.jpg)

回想五到十年前，工程社区大量讨论上下文切换的成本。讨厌同事在你干到一半时走到桌前：再回到心流要很久——我刚才在哪儿？在干什么？哪怕桌上还有点残留，也要时间。

我们现在切换得比以前更凶。不在软件工厂里时，我一天可能同时跟 Agent 做五到十个项目，或同一项目上五到十个功能——也可以说五到十个会话。

那意味着我至少得盯住其中几个。若我信得过任务定义够清、结果够清、验证做得够好，可以把部分任务的自主性开大。但也有任务我不那么放心——风险更大或更绕——就得亲自盯。

考虑把软件工厂优化成「为审的人」服务。既然每条路最终仍汇到一个人的注意力，你该问：工厂让你仍要做的那些决定，便宜了多少。

## [做错项目的失误](#a-wrong-project-mistake)

我记得跟 Agent 并行多个项目时，有几次不小心：比如在做一个要加暗色模式的 Web 应用，脑子里已经想好形状，却进错了另一个项目的会话，把同一条提示词丢进去了。

于是给一个完全不需要暗色模式的东西开始实现暗色模式。人会犯这种错。我不想让软件工厂也犯。

你得把它当系统想。你实际上是在把软件工程文化、团队文化编码进系统，让它有同类行为，让所有权有落点，让有人对结果负责，并对这些想法定得很清楚。

## [全绿时也可能骗人](#when-green-is-misleading)

即便在这些系统里，也要非常小心。很多人都见过：让 AI 帮你过测试——编程题、单元测试——它可能改测试来满足条件，也可能改代码逻辑来过条件。那不代表它按你的意图，同时对齐了功能行为与测试本该测的东西。

![](https://pbs.twimg.com/media/HQrNGlRaIAAH9cw.png)

工厂显示全绿，不等于真绿——尤其刚搭起来时。你得大量注意：检查、验证是否长对形状、是否在做你期望的事。别被误导。

你也不想看到这种：测试说我改了支持的鉴权提供方；你让我加 GitHub 登录，但我的 UI 只摆得下三个，于是我丢掉了另一个——而那个恰好是客户想要的。系统怎么工作，要说得非常清楚。

另外安全超级重要：若工厂读不受信输入（GitHub issue / Slack 消息），可能是对抗性的，带供应链攻击等问题。一些软件工厂产品，如 [Vercel](https://vercel.com/blog/building-a-software-factory-for-ai-sdk) Sandbox / AI ADK Factory，把 Agent 放在隔离沙箱里，只持任务需要的密钥。这样一次被攻破的跑法够不到用不到的东西。防御最终是分层的。

## [哪些旧项目值得再活一次？](#which-old-projects-deserve-another-life)

我觉得如今工作的一大部分，是决定什么该存在。AI 之前那么多年，多少软件工程项目、周末项目、个人项目半途而废：没时间做完，排不出优先级，因为没那么重要或抽不出时间。

现在把那些项目做完相当容易，但同样的人判断问题回来了：这些项目配存在吗？该上线吗？一旦放进世界，哪怕只有五个用户，你可能也得维护；你可能有了想守住的质量门槛。

这些年我有很多 GitHub 项目；现在有了 Agent，第一件事是先让它能构建。当然，你一 clone，依赖全变了，建不起来；一半过时或到处是安全洞，得更新。

然后若没有测试，你得加测试，好知道升级或迁到更现代语言 / 框架时行为还在。

接着你会问：傻例子，当年用 Twitter Bootstrap，现在人人用 Tailwind 和 shadcn，得重做 UI。你会发现这突然更费时间——Agent 能更快干完很多活，但你要把产品感与品味算进去。

你仍会问：给谁用？有市场吗？给自己还是给别人？放进世界后，是否还像以前那么有意思——现在谁都能同样快地转起来？

所以「这些东西配存在吗？」「怎么把品味与判断算进去？」我觉得仍然极其重要。稀缺的人注意力仍落在这里。以前一天只有有限小时，还有会，还要给设计与编码预算时间。

现在有 Agent 帮忙，你更得清楚：时间花在哪、为什么。

## [我搭了一个样例之后发生了什么](#what-happened-when-i-built-a-sample-one)

接下来说 82 分钟的工厂跑法。一直有人问：「怎么建软件工厂？」或「我习惯 Claude Code / Codex，怎么演成软件工厂？」

我先说的是：「你也许完全没事。你的工作未必需要工厂。」但我仍想给一个可对照的参考设置。我做了仓库 [Factory](https://github.com/addyosmani/factory)，还有[演示应用](https://github.com/addyosmani/factory-demo/)和[工作坊](https://github.com/addyosmani/factory/blob/main/ADVICE.md#:~:text=step%2Dby%2Dstep%20workshop)。

过去几年我的演示应用多半是电影 App——我爱看电影。演示从很简单的电影 App 起步。我想让工厂实现若干功能：收藏、搜索、暗色主题之类。

于是让工厂开工。你可以去看实现。好处之一是真抓到了问题——若只做一次 one-shot 实现，我未必抓得到。

大概到第 60 分钟，我觉得「怎么异常慢」。我问 harness / 工厂为什么慢。它说：其实完全正常，验证器都还在跑。

你或许期望单任务 10、15、20 分钟；一旦加上验证、重试、浏览器检查、人审等额外延迟，往往要两到四倍时间。

我确实觉得这些能换来更好质量与对系统的信任。度量上可以看每合并 PR 的成本、代码货架寿命，当作理解债指标。

你还得区分：有用延迟 vs 工厂开销。我这边验证器抓到了真问题；一点时间沉在我想要的证据上；一点是工厂本身开销。我没怎么优化它，但一个狂跑你觉得没价值的检查的工厂，不等于高质量。

对任何重复检查，要研究：是否无关？是否吵？是否真让系统更安全？

## [验证需要预算](#verification-needs-a-budget)

我怎么想验证预算——就是我们在说的验证预算。跟我历史上想性能预算的方式一样。

![](https://pbs.twimg.com/media/HQrNOSabUAAXcau.png)

有些检查可以在软件开发生命周期很早跑；有些很重但价值极大，你会想稍后跑。快检查如 lint、类型检查，可以很早。

完整测试套件可以靠近 draft PR 前后跑：变异测试、浏览器测试、安全检查等。

我不想用摘要取代这些——要真测试——但得把预算摆对地方，别拖垮开发环。我当然从不想拖慢开发环；快迭代对我很重要，同时仍要制衡。

## [一次跑法没有上线时](#when-a-run-doesnt-ship)

上面很多写的是检查。

在他们的软件工厂里，Vercel 把[每次 Agent 跑法](https://vercel.com/blog/building-a-software-factory-for-ai-sdk)标成 “success”、“flawed”、“blocked” 或 “manual”，只有 “success” 进生产，其余重新进系统。我也按类似说法想跑法。

![](https://pbs.twimg.com/media/HQrNq-bbcAArs4J.png)

这里 “Flawed” 表示做了错的东西，或上下文不全，必须修。Blocked 表示环境可能缺凭证，得你补上。Manual 是工厂尚不许越过的边界。

三者里两个可能有机械修复，最后一个关乎信任。

分类虽好，却不显示成本。回到我用 TMDB App 的工厂实现：无拒绝的 quick finder 花了 7 分钟；收藏功能两次拒绝、中间一次人决策，花了 56 分钟。同一座工厂。所以我会把分类与分阶段计时配对，否则你只知道跑法 flawed，不知查清楚花了多少。另一处我会修的是边界交接：样例工厂停掉第一个 issue，移到 factory:needs-info，这是对的，但我不知道答案该写哪儿。Manual 跑法不是工厂停下就算完，而是人知道下一步该干什么时才完。

## [自主性不是一个旋钮](#autonomy-is-not-a-single-setting)

几周前我写过一篇关于 [agentic 自主性](https://addyo.substack.com/p/agentic-autonomy-levels)的文章：怎么想自主性——每个项目不会只有一个旋钮。

验证买来信任，也买来给 Agent 更多自主性的能力。例如我做非琐碎改动，检查到位、验证正确，或许还亲手看过；下次同项目同类任务，我可能更敢给 Agent 多一点自主。

建软件工厂时要想的就是这个。验证会随风险变。目标是最好的信噪比。不要只堆一份巨大检查清单。

## [我不得不重学的功能](#the-feature-i-had-to-relearn)

有一天我用多个 Claude 会话，同时几个项目、每项目几个功能；有个功能我一直拖着。Claude 实现了它，测试看起来过了。我没怎么想验证，测试过了，我就以为行了，合并了。

那是个收藏功能。我觉得还不错。浏览器里看也像没事。几天后我想微调，又回到代码。

我不想只让 Agent 改——只是点击图标时触感不对，我想自己搞懂怎么运作，才能正确带 Agent。

回到代码，我却讲不清这功能怎么工作。仓库是我的；我批准过改动；仓库很多部分我懂，但理解没跟上堆起来的代码。

我没吸收的是：加进去的功能怎么工作、UI 怎么工作、效果怎么工作。我不得不重做，一步步问：「这怎么走？我怎么才能懂？」

## [并行工作对理解做了什么](#what-parallel-work-does-to-understanding)

并行会放大这整个问题；放进软件工厂更放大。五到十个会话，制造的不只是评审量问题——还制造多个心理模型，你在别处干活时它们会凉掉。

我们历来谈上下文切换的难；一旦聊天压缩、你否掉一些路径、试别的、跟 Agent 结对，就很难记住会话里发生的一切。

你可以往上滚；压缩发生后不会全在，也不可能全装进脑子。代码常保住做了什么决定，却不保住为什么。

这对你可能有用：在重要处，考虑让 Agent 把轨迹、或解题时有意思的教训存下来，方便以后回看。

这可以提交进仓库，也可以只留本地，也可以跟团队共享；之后可以查阅，而不是依赖它还在会话里，或你以后还记得。

## [它到底在造什么？](#what-does-it-actually-make)

@threepointone 和 @bentlegen 发过一些关于软件工厂的[看法](https://x.com/threepointone/status/2091167009669075314)[与](https://x.com/bentlegen/status/2091511818355147204)看法，我很同意：

![](https://pbs.twimg.com/media/HQrScX6bQAA9njs.jpg)

![](https://pbs.twimg.com/media/HQrUnqha0AA4vTC.jpg)

人很容易迷上「做」的机械，优化机械，却忘了本该产出什么。若你的工厂主要产出一座更好的工厂，你建的软件产品就是它自己。

我觉得投资这个环没问题，它会复利。失败是环闭合了：工厂产出的一切都被工厂自己吃掉，外面没人会在你关掉它时注意到。我用的测试是拉力（pull）：外面得有东西在要这份改进。说不出谁在拉，你就是在抛光。

## [所有权不会消失](#ownership-doesnt-disappear)

底下有条更宽的原则。

人手敲的代码比例可能大幅下降。我不认为人的所有权必须跟着降。

- 仍有人选择问题。

- 仍有人选择架构。

- 仍有人设定质量门槛。

- 有人决定哪些验证信号值得信任。

- 有人决定证据何时够上线。

系统坏了时，「Agent 写的」不够用。所以我不觉得软件工程的未来最好描述成「人离开环」。相反，**人的判断正在换位置。**

我们该把人从机器能给出更强、更快、更确定信号的环段里拿开；同时把人集中到上下文、品味、风险与长期所有权最要紧的地方。

最好的软件工厂，不会以多彻底消灭人参与来定义。

而会以多聪明地**安放**人来定义。

把人判断放在上游：意图、系统形状、质量门槛。在自动化背压变弱、或后果变主观的地方审代码。把每个确定信号尽量早、尽量持续推进环里。随系统赢得或失去信任，有意收紧或放松约束。

**最终上线的代码，仍得有人拥有。能上线的代码，仍始于有人在乎它该不该存在。**
