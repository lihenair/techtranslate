# 在 Uber 的规模上高效运转一座「软件工厂」

原文链接：<https://x.com/UberEng/status/2093444169037762840>

原文作者：Uber Engineering（文章作者 @udaykiran）

![文章头图](https://pbs.twimg.com/media/HQ1LPdZasAAsgNT.jpg:large)

作者：[Uber Engineering](https://x.com/UberEng)（文章作者 [@udaykiran](https://x.com/udaykiran)）

发布于 2026 年 8 月 28 日。

**在 Uber，AI 工具如今已嵌入软件开发的每一个环节。要在使用量涨了 7 倍的同时把各项单位成本压下来，靠的不是压供应商的单价，而是把「零价值的 token 消耗」一项项挤掉。**

## [引言](#introduction)

在 Uber，AI 工具现在已经嵌入软件开发的每一个阶段。超过 70% 的拉取请求（pull request，PR）都归功于本地或云端 agent。工程师们在整个软件开发生命周期（SDLC）里搭了 3,600 多个 agent 技能，每天执行的 agent 技能调用超过 3 万次。

在 AI Engineer 2026 大会上，我们分享了对「软件工厂（Software Factory）」的[愿景](https://youtu.be/17-YSUHo6Lk?si=EbqFAc2UwHX_3wSc)，以及我们正在整个生命周期里搭建的各种构件和托管 agent（managed agents）。随着这一愿景推进，越来越多的会话不再由人发起，而是由自动化的托管 agent 处理：代码评审、自愈式修复 CI 失败、带视觉校验地完成端到端（E2E）PR、分诊 on-call（值班）告警、调试新提交的 bug，以及各种带人工评审 / 升级的代码维护任务。

如图 1 所示，从 2026 年 2 月到 8 月，我们所有员工（工程师与非工程师）在全部 agent 化产品上的周活跃用户涨了 7 倍，周 agent 请求量涨了 9.4 倍。与此同时，得益于全面优化，我们的 AI 总支出自 4 月起相对稳定了下来。

![图 1：周活跃用户与周 agent 请求量的增长](https://pbs.twimg.com/media/HQ1lFqXbMAA58qf.jpg)

由于采用率、工作负载构成和模型升级都在持续变化，要单独隔离出「我们自己的优化收益」，就得固定住某一个模型不变——因为每次升级、每换一个模型家族，行为都会漂移。我们在 2 月到 7 月间就是这么做的：每 1,000 次模型请求的成本，比峰值下降了将近 34%；每会话成本，比 6 月的峰值下降了 52%。

![每千次请求成本与每会话成本的下降](https://pbs.twimg.com/media/HQ1lY8pa0AArbuP.jpg)

这篇博客会讲清楚我们是怎么看待自家软件工厂的：agent 会话运行所在的四个层次、我们用来拆解支出的成本方程、我们怎么度量其中每一项，以及怎么在每一层上优化这些项。

本文对比里用到的所有定价和厂商指标，都基于公开信息；成本效率的提升，来自在标准分层定价内更聪明地路由我们 Uber 内部的工作负载。我们测到的具体成本降幅是我们环境所独有的，你那边的结果会因代码库、团队规模和 agent 工作流而异——但「用真实工作做基准、既优化准确率又优化成本」这套方法论，是放之四海皆准的。

## [优化「单 token 价格」](#optimizing-price-token)

单 token 价格由厂商定，而由我们来挑哪个模型跑哪种工作负载。在我们所有托管 agent 的各层里，我们都为该工作负载挑最帕累托最优（Pareto efficient）的那个模型。对我们来说，帕累托最优意味着：每完成一个任务的成本、输出质量，以及模型可靠性三者的权衡。

**基准驱动的模型选择**

模型选择分四步走，每一个托管 agent 都一样：

- 用该 agent 的真实工作做出一个基准。

- 让 agent 跑在一个 harness 上——它在同一个接口后面能接任意模型，前沿的或开放权重的都行。

- 迁移到帕累托最优的那个，并且持续迁移。前沿每隔几周就会挪一次。

放眼未来，我们会持续利用从托管 agent 聚合而来的洞察，去测试和部署各种模型路由策略，从而不断打磨工作负载的表现。

举个例子，我们用 uReview 来为所有 PR 做 AI 代码评审。它的基准是从「已知有 bug」的真实 PR 里建起来的，并按易、中、难分级。我们对照这些 bug 打出精确率（precision）、召回率（recall）和 F1，再加上每次评审的成本、延迟、超时和噪声。如图 5 所示，切换模型既提升了 F1，又大幅降低了每 PR 成本。图中虚线是帕累托前沿，位于它左下方的一切，都被某个更便宜或更好的方案打败了。

![图 5：切换模型后 F1 提升、每 PR 成本下降（虚线为帕累托前沿）](https://pbs.twimg.com/media/HQ1mDZzasAAPKJn.jpg)

我们内部还有一个 Uber SWE 基准，用横跨我们大型单体仓库（monorepo）的数千个真实 PR，让前沿模型和开放权重模型跑各类任务。我们用它来指导所有 SDLC 托管 agent 的模型选择。

**默认模型选择**

在交互式界面里，单 token 成本是固定的；不过你可以有策略地在不同模型间调配 token 的分布。主要有两个默认设置在左右这个分布：会话初始模型，和子 agent 模型。

子 agent 的默认设置，被证明是最有影响力的一根杠杆，而且其分量还在持续变大。随着最新模型能力让多 agent 编排更有效，发起子 agent 的会话占比一直在稳步上升。因为子 agent 干的是输入明确、定义清晰、往往不需要前沿级推理的活儿，我们默认让它们用一个更弱、更划算的模型，同时仍允许手动覆盖。主模型负责任务拆解与评估，子 agent 负责执行。

## [优化「每请求 token 数」](#optimizing-tokens-request)

每一轮都会重新发送完整的对话历史、项目上下文和工具结果。任何能减小单请求负载的东西，都会在整个会话里被放大。

**默认配置**

所有交互式 harness 都用同一个统一封装来处理安装管理、配置、鉴权和成本可见性。有两项标准化的默认配置，直接压低了每请求的 token 消耗：

- **即便是 100 万上下文窗口的模型，也在 40 万 token 处触发自动压缩（compaction）：** 这个阈值在模型表现与缓存突刺、重复输入 token 成本之间做了平衡。我们的测量显示，全机队范围内每请求的输入 token 有了显著下降。

- **推理强度默认设为「中」：** 在主模型上，输出 token（包括内部推理 token）的计费是输入 token 费率的数倍；这条策略调整，直接压低了成本最高那一类 token 的支出。对一大类任务来说，「中」等推理在成本与质量之间取得了不错的平衡。

**Prompt 缓存策略**

我们的 prompt 缓存（prompt cache）策略，由供应商缓存读写的经济账驱动。既然每一轮都要重传完整对话历史，那把前面的上下文缓存起来，就能避免反复支付全价，让后续读取只花标准输入 token 费率的 0.1 倍。不过写入溢价各不相同：5 分钟的缓存条目费率是 1.25 倍，1 小时的则是 2 倍。因此选一个最优的 TTL（存活时间）取决于两轮之间的间隔时长。可选的 TTL 有 Anthropic® 的 5 分钟和 1 小时，以及 OpenAI® 的 30 分钟。

![prompt 缓存的 TTL 与读写价格](https://pbs.twimg.com/media/HQ1mSBhakAAEMpx.jpg)

因为工程师常常让交互式会话空闲超过 5 分钟，我们从默认的 5 分钟 TTL 切到了 1 小时窗口。这些频繁的空闲间隙，以前会让前缀缓存失效，逼着系统按全价重建上下文。相比之下，子 agent 仍保留 5 分钟的缓存 TTL，因为它们的执行只聚焦于单个、短命的任务。

**通过 Shell 执行 MCP 工具**

在 Uber，所有 MCP（Model Context Protocol，模型上下文协议）交互都经由一个统一网关路由。这个单一入口涵盖了 1,000 多个 MCP 服务器，横跨内部和第三方 SaaS MCP，实现了集中式的鉴权与策略执行。

但标准 MCP 会把所有工具的 schema 直接加载进每一个会话，不管工程师在那个会话里到底会不会调用它们。举个例子，装了 100 多个工具时，这种预加载会给初始提示词平添大约 5 万到 7 万 token 的 schema 开销，而这些开销随后会在每一轮上下文里被重新发送。

![MCP 工具 schema 带来的上下文膨胀](https://pbs.twimg.com/media/HQ1mfIPagAASfyo.jpg)

为了对付这种上下文膨胀，我们引入了两个互补的优化机制：

- **CLI 工具解析：** 用「让模型执行一条 shell 命令」来取代直接的 MCP 集成。CLI 会在调用时动态地针对网关解析并调起所需工具，从而把 Uber 的 MCP schema 从会话上下文里彻底清出去。我们内部 MCP 网关上全部 1,000 多个 MCP 工具，都被投射成了 CLI 命令。

- **工具搜索：** 通过让模型搜索工具目录、按需只加载所需工具，来扩展到数千个工具。这个办法缓解了上下文膨胀，通常能减少工具定义占用的 token，并在可用工具库不断扩大时仍保持很高的选择准确率，避免了大工具集带来的性能退化。

**Code-Mode**

当工具以 shell 命令的形式直接调用函数时，模型就能把多个动作打包进同一个脚本。对那些「话痨型」的工具协议，这种打包尤其有利。在标准 MCP 工作流下，每个动作都要占一个单独的模型轮次：发出请求、把原始响应载入上下文窗口、再顺序处理结果。比如，执行一条 SQL 查询，就得提交请求、轮询状态 2 到 5 次、再取回输出。Code-Mode 把这整套流程收进一个自动化的 Python 循环里，让中间的轮询待在模型的活动上下文之外。如图 8 左侧所示，模型参与到轮询循环里，每一次响应都落进它的上下文；而右侧，循环在一个子进程里跑，只有摘要会回传。

![图 8：左侧模型参与轮询循环，右侧循环在子进程中运行、只回传摘要](https://pbs.twimg.com/media/HQ1mthGbgAAoz7D.jpg)

我们在同一个会话里，让 5 条相同的 SQL 查询分别走两条路径，来做了测量：

![同一会话中两条路径跑 5 条相同 SQL 查询的测量结果](https://pbs.twimg.com/media/HQ1QrckawAACSTT.png)

前三行点出了主要发现：哪怕结果集极小、远低于响应大小上限，Code-Mode 也能把 token 用量减少 50% 以上。这些效率提升并非来自绕开大数据负载，而是来自消除不必要的开销，包括 schema 初始化、多轮轮询，以及冗余的逐步推理。

批量工作流会把这个效果叠加放大：本来要 N 个模型轮次的循环，变成了一个脚本，节省因此累积到 90% 以上。通过为我们访问最频繁的 MCP 服务器部署 25 个以上预建的 Code-Mode 技能，我们确保标准工作流默认走上最划算的那条路。

**SaaS MCP**

管理第三方软件，被证明比管理我们的内部服务器难得多。厂商设计 MCP 服务器时，会把完整的产品能力都暴露出来，因为他们没法预判某个客户的具体用法。比如，某个办公套件把 49 个工具塞进一个服务器，光 schema 就要约 2.2 万 token；而消息类和项目跟踪类厂商分别塞了 34 个和 46 个工具。加载两三个厂商的服务器，会让 agent 在用户还没输入提示词之前，就背上比被编辑文件还多的 schema 开销。

为了对付这个，我们用与内部 MCP 相同的机制，把 SaaS MCP 服务器也经由 MCP 网关路由，并把这些 MCP 全都暴露成任意 agent 界面都能调起的 CLI。此外，我们在 Code-Mode 插件里为每个服务器编写专门的技能，把常见工作流封装起来。这在众多 SaaS 厂商上解锁了高效的 agent 工作流。

![把 SaaS MCP 经网关统一接入](https://pbs.twimg.com/media/HQ1m6-ga4AAxR4d.jpg)

## [优化「每轮请求数」](#optimizing-requests-turn)

一个缺乏「落地信息（grounding）」的 agent，不是便宜地失败，而是缓慢地失败——它会反复把越撑越大的上下文窗口发出去，只为多搜一个地方。预先提供更丰富的信息，仍是减少这种搜索开销最强的一根杠杆。

**上下文工程**

在 Uber 那庞大的代码库与数据生态里——数亿行代码、数千张表——agent 的大部分轮次都花在「定位信息」而非「生成代码」上。为此，我们造了一张 AI 上下文图谱（AI Context Graph）：一个统一网络，含 2,400 万个节点、8,000 万条边，涵盖 86 种节点类型和 117 种边类型。它整合了 30 多个内部系统的数据，包括服务、工程团队、事故日志、PR、架构设计文档、部署、数据集，以及历史表使用查询，并让任意 agent 都能用自然语言去查询它。

![AI 上下文图谱](https://pbs.twimg.com/media/HQ1nFogagAAh5yy.jpg)

有落地信息的 agent 查询了历史用量，认出了那张被 50 多位分析师用过的具体的表，38 秒就给出了答案。反过来，没有落地信息的 agent 对那张表毫无可见性；它花了 20 分钟去翻服务代码、派出 2 个子 agent、撞上 3 个错误，最后还错误地断定那个数据集没法查询。

## [可见性与教育](#visibility-education)

这里的杠杆，是那些能帮工程师和 agent 更快收敛的可见性与反馈回路。

**状态栏**

我们在 harness 的状态栏里放了一个实时成本计数器，既跟踪每个 harness 的实时支出，也跟踪每个用户在所有 harness 上的实时支出。

![harness 状态栏里的实时成本计数器](https://pbs.twimg.com/media/HQ1nQaybsAA_Hju.jpg)

**可见性与支出分层**

为了不去强加硬性上限，我们上线了实时支出跟踪和自动化的「轻推（nudge）」：

- **状态栏实时计数器。** 当前会话成本始终显示在终端里。

- **harness 额度池。** 所有交互式 harness 共享一个额度层，而不是按工具分预算；托管 agent 则用单独的额度层。

- **Slack 轻推。** 在达到预期支出的 50% / 80% / 100% 时告警，好让工程师有时间规划。

- **便捷的审批流。** 额度升级由经理签字，且能快速生效传播。

- **成本检查技能与提示。** 一个按需拆解成本的看板技能，外加状态栏里的实时指导。

这些让工程师能独立评估任务的投入产出比（ROI），同时遏制住失控的开销。

**会话分析看板**

状态栏虽能凸显一个会话的总花费，却看不到成本的驱动因素，也给不出可执行的提效步骤。泛泛的指南能提供高层原则，却没法评估某个开发者的具体工作流。会话分析看板通过直接检视会话产物，弥合了这道缺口。

它直接内建在运行时里，零配置、无需选择加入。执行「成本看板（cost dashboard）」技能，会分析该用户在所有 harness、横跨本地与远端云沙箱的全部会话轨迹。它不是产出一个聚合指标，而是在各会话里标记出 16 种不同的反模式，并给每一种都配上其财务影响和一条有针对性的补救建议。其中一些类别包括：

- **次优的模型路由：** 把 Sonnet 就能轻松搞定的简单多轮会话，放到 Opus 上去跑。

- **上下文窗口膨胀：** 大块的 MCP 负载（比如 40KB 的响应）滞留在上下文里，在后续轮次里被反复计费。

- **缓存过期带来的低效：** 长时间中断后再恢复会话，过期的 prompt 缓存逼着系统按全价重建前缀。

- **提示词初始化开销：** 在用户还没有任何输入之前，就预加载了 10 万 token 的系统指令和工具定义。

![会话分析看板：标记反模式及其成本影响](https://pbs.twimg.com/media/HQ1PdF3a8AAqUHN.jpg)

**下一步做什么？**

正在推进的当前举措包括：

- **扩大托管 agent 机队：** 对每一个新 agent，我们都遵循一套一致的路线图——确立目标产出指标、组装评估基准、找到帕累托最优的模型。这套系统化的做法，旨在把 SDLC 的每一个阶段都往「工厂成熟度模型」的更高处抬。

- **动态模型路由：** 我们正在把基准覆盖扩展到多样的编程语言、代码仓库和 agent 形态上。既然模型能力千差万别，有效的模型路由就高度依赖全面的评估。

- **深化上下文图谱集成：** 我们正在把图查询能力，解锁到更广泛的自主 agent 上。

- **把会话分析进化成实时的开发者指导：** 通过从「周期性批量检测反模式」转向「持续的轨迹监控」，我们希望把个性化、实时的提效建议，直接送到工程师面前。

- **技能的持续改进：** 我们正在做一套自动化机制，记录 agent 技能执行中的小痛点，并从收集到的轨迹里自动生成技能更新。

## [结语](#conclusion)

管住并压低不断上涨的 AI 编码开销，同样是一个可解的工程难题。靠「消除被浪费的、零价值的 token 消耗」，而不是单纯依赖更低的单价或降级工具，我们把使用量扩大了 7 倍，同时在所有指标上都降低了单位成本，并且改善 / 维持了输出质量。

核心的战略转变，是从交互式的开发者工作流，转向完全托管的 agent。把 SDLC 工作负载迁进托管环境，让我们对模型路由、执行 harness 和运营支出有了完全的掌控。优化一支专门化托管 agent 的机队——每个都配着专属的评估基准和一个帕累托高效的模型——本质上比「在成千上万名工程师身上逐个优化终端会话」更划算、也更可扩展。
